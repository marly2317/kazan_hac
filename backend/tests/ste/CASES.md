# Тест-кейсы подбора КТРУ (`cases.jsonl`)

120 запросов поставщика с ручной («серебряной») разметкой: какое семейство КТРУ, какой лист,
какая стадия ответа и какие сигналы ошибок ожидаются. Используются для прогона пайплайна
(`python -m apps.ste.eval`, архитектура §3.11) и как регресс для поиска (`--retrieval`).
Целостность разметки проверяет `test_cases_valid.py` — без LLM и сети, меньше секунды.

## Как собраны

1. **Источник — реальные СТЕ.** Из выгрузок `materials/Инструменты (2).xlsx`, `Мебель.xlsx`,
   `Одежда.xlsx` (лист «Лист1», ~100 тыс. строк в каждой) отобраны карточки по ключевым словам
   типа товара (УШМ, шуруповерт, стол письменный, костюм, ботинки…), у которых **есть семейство
   в базе знаний**. 47 кейсов ссылаются на исходную карточку (`source_ste_id`); остальные
   написаны по образцу типичных карточек того же типа.
2. **Тексты написаны вручную** (без LLM) так, как поставщик набирает в портале: полный текст с
   брендом и моделью, короткий («шуруповерт сетевой»), без ключевой характеристики, разговорный
   («болгарка», «худи», «стул ИЗО», «валенки»). Бренды, модели, цвета, размеры одежды — шум,
   который должен уйти в бренд/модель/дополнительные характеристики.
3. **Каждая метка проверена по КБ** (`kb/ktru_kb.json.gz`) скриптом разметки: для «золотого»
   разбора текста (что извлёк бы безошибочный LLM-2) значения сопоставлены с допустимыми
   значениями КТРУ с учётом строгих/нестрогих границ и перевода единиц (`units.convert`), а листья
   сужены по правилам §4.5 (уверенное несовпадение исключает лист, отсутствие характеристики —
   нейтрально). Отсюда `expected_leaf` и `expected_stage`; затем каждую метку просмотрели глазами.
4. Демо-сценарии §9 перенесены дословно (`demo-01…10`), для сценариев 9–10 текст конкретизирован.

## Поля

| Поле | Смысл |
|---|---|
| `id` | `demo-NN`, `tool-NN`, `furn-NN`, `cloth-NN`, `shoe-NN`, `bag-NN`, `err-NN`, `typo-NN`, `abs-NN` |
| `category` | категория семейства из КБ (`инструменты`, `мебель`, `одежда`, `обувь`, `сумки и рюкзаки`) или `вне охвата` |
| `variant` | `full` · `short` · `missing` · `colloquial` · `demo` · `error` · `typo` · `absent` |
| `source_ste_id` | ID СТЕ из выгрузки, по которой написан текст, или `null` |
| `expected_family` / `_name` | корень семейства КТРУ; `null` — товара в охвате КТРУ нет |
| `acceptable_families` | другие семейства, выбор которых тоже защитим (для `absent` — только общие позиции) |
| `expected_leaf` | код листа, **только если** текст однозначно определяет лист по сигнатурам КБ |
| `expected_stage` | `done` (лист определён) · `question` (семейство ясно, листьев > 1) · `conflict` (значения исключили все листья) · `not_found` |
| `expected_signals` | **минимальный** набор ожидаемых `SignalType`; прочие (`MISSING_REQUIRED`, `QUOTE_NOT_FOUND`) не запрещены |
| `expected_values` | 1–3 ключевые характеристики → значение КТРУ ровно как `AllowedValue.describe()` («≥125 <130 Миллиметр»); kind=3 — списком |
| `notes` | почему метка такая, на чём может споткнуться система |

Стадии: `done` 88 · `question` 18 · `conflict` 5 · `not_found` 9. Охвачено 62 семейства КБ,
88 кейсов с листом, 14 с допустимыми альтернативами.

Ошибки (12 + демо 7–8): `OUT_OF_RANGE` ×5 (матрац 5 м, ранец 45 см, посадочное отверстие
22,2 мм у торцовочной пилы, фартук на рост 210 см, реноватор 320 Вт — реальная «дыра» в КТРУ
между «≥250 <300» и «≥350 Ватт»), `UNIT_MISMATCH` ×4 (толщина в кг, диаметр диска в Вт, объём
рюкзака в кг, ёмкость аккумулятора в вольтах — число не к той характеристике),
`VALUE_NOT_ALLOWED` ×3 (патрон SDS-plus у шуруповёрта, стеклянная столешница письменного стола,
двери-рольставни архивного шкафа), `CONTRADICTION` ×2 («мужская женская», «аккумуляторный…
только от сети»). Опечатки: раскладка целиком и в одном слове, пропуски и перестановки букв.
Вне КТРУ: отвёртка, перфоратор, сверло по металлу, уровень, набор инструментов, квадрокоптер,
ноутбук, «абвгд».

## Как читать метки

- **Лист определяется kind=1.** `expected_leaf` ставится, когда текст задаёт все различающие
  неизменяемые характеристики (Вид, Тип питания, Пол…) прямо или очевидным синонимом
  («болгарка» → «Углошлифовальная машина», «каркас ЛДСП» → «Деревянный»), либо семейство из
  одного листа. Тест требует, чтобы `expected_values` **сами** сужали семейство ровно до этого
  листа — метка «done» не может держаться на неявном знании.
- **`question` — семейство ясно, листьев несколько.** Тест требует, чтобы по `expected_values`
  оставалось ≥ 2 листьев. Особый случай `cloth-06`: обе kind=1 известны, но два листа
  различаются «Половой принадлежностью» с kind=2 — КТРУ так устроен.
- **`conflict`** — уверенное значение (единица распознана, размерность совпала) не попадает ни в
  один допустимый интервал у всех листьев (§4.6). **`UNIT_MISMATCH`** даёт слабое значение,
  оно листья не исключает, поэтому такие кейсы — `done`/`question`, а не `conflict`.
- **`absent`** — честное «не нашли» (`not_found`, сигнал `NOT_FOUND`). Общая позиция («Инструмент
  ручной прочий») — запасной вариант §4.2, перечислена в `acceptable_families`.

## Оговорки

- **Метки ручные (серебряные).** Это одна защищённая трактовка, а не единственная. Где КБ
  допускает несколько семейств (дрель-шуруповёрт → «Шуруповерт» или «Дрель ручная
  электрическая»; рабочий халат → «Халат производственный» или спецодежда от ОПЗ; ботинки с
  металлическим подноском → отдельное семейство или «Обувь специальная… от механических
  воздействий»), они перечислены в `acceptable_families`. `expected_leaf` относится только к
  `expected_family`: верное альтернативное семейство даст другой лист.
- **Эквивалентные сигналы.** «Значение не из списка» модель с enum-схемой может вернуть как
  статус «противоречие» → `CONTRADICTION` вместо `VALUE_NOT_ALLOWED`; «мужская женская» может
  стать `DUPLICATE_VALUE`. Метки называют основной сигнал, допустимая замена — в `notes`.
- **Стадия после первого ответа.** `expected_stage` — исход `analyze` без ответов пользователя.
  Кейсы с `MISSING_REQUIRED` не размечены: дозаполнение — норма для `done`.
- **Неоднозначности самого КТРУ** отмечены в `notes`: ширина строгания 82 мм попадает и в
  «= 82», и в «= 82,4» (допуск 0,5 %); «2 ящика» — в перекрывающиеся «≥1» и «≥2 Штука»; в
  `demo-04` «ЛДСП» без уточнения можно отнести к каркасу — тогда лист определится сразу.
- **Распределение по стадиям** смещено к `done` (73 %): тексты из реальных карточек обычно
  называют тип товара. Сценарии «не хватает kind=1» собраны в `missing`.
- **Опечатки** проверяют связку корректор → пайплайн; при поиске без корректора (`--retrieval`)
  кейсы с раскладкой ожидаемо проваливаются.
