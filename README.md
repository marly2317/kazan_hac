# Автозаполнение ключевых характеристик в СТЕ

Решение задачи Tender Hack (Казань, 2026): пользователь описывает товар своими словами — с
опечатками и не до конца, — а сервис определяет характеристики, приводит значения и единицы
измерения к справочнику КТРУ и поэтапно сужает множество кодов до одного.

**Django 6.1 + DRF** на бэкенде, **Vue 3.5 + TypeScript** на фронте, всё поднимается одной
командой через Docker Compose. Подбор — детерминированный: триграммное сходство, SymSpell по
словарю КТРУ и проверка значений по самому справочнику. Внешних LLM в основном пути нет.

| | |
| --- | --- |
| Точность@1 на наборе из 26 описаний | **100%** |
| Верное воздержание там, где позиции в КТРУ нет | **100%** |
| Время ответа | медиана **39 мс**, максимум 198 мс |
| Тесты | 190 бэкенд + 23 фронтенд |

Замер воспроизводится: `python3 scripts/eval.py --verbose`. Набор маленький и составлен
вручную — это защита от регрессий, а не оценка на независимой выборке.

## Главное решение

**Уверенно неверный код КТРУ хуже честного «не нашли».** Пользователь не может проверить код —
он за ним и пришёл. Поэтому везде, где можно было угадать, сервис воздерживается и говорит,
чего ему не хватает.

Это не абстракция: на запрос `отвертка крестовая PH2 длина 150 мм` первая версия отвечала
`Очки для защиты от радиации` со статусом «код определён». Отвёрток в КТРУ нет вовсе — во всех
183 архивах нет ни одной позиции с «отвертк» в наименовании вне медицинской группы, — а поиск
по сходству не умеет возвращать «ничего». Подробности — в
[docs/ALGORITHM.md](docs/ALGORITHM.md).

## Запуск

```bash
cp infra/.env.example infra/.env
# заполните DJANGO_SECRET_KEY и POSTGRES_PASSWORD:
python3 -c "import secrets; print(secrets.token_urlsafe(64))"

cd infra && docker compose up --build
```

Приложение открывается на `http://localhost:8080` (порт задаётся `PUBLIC_PORT`).
Чтобы получить готовую учётную запись, поставьте `SEED_DEMO_USER=1` — создастся
`demo@example.com` / `demo-password-2026`. В реальном развёртывании этого делать нельзя.

Учётная запись администратора:

```bash
docker compose exec backend python manage.py createsuperuser
```

## Архитектура

Один процесс на бэкенде и одна сборка на фронте, но внутри — независимые модули, и каждый
разрезан на четыре слоя. Зависимости направлены **внутрь**: наружный слой знает о внутреннем,
обратное запрещено.

```
presentation  →  application  →  domain
      ↓               ↑
 infrastructure ──────┘   (реализует порты, объявленные в application)
```

| Слой             | Что внутри                                        | Чего там быть не может   |
| ---------------- | ------------------------------------------------- | ------------------------ |
| `domain`         | сущности, правила, ошибки                          | Django, DRF, HTTP, Vue   |
| `application`    | сценарии (use cases), порты, DTO                   | ORM, `fetch`, сериализаторы |
| `infrastructure` | ORM-модели, репозитории, HTTP-шлюзы, миграции      | бизнес-правила           |
| `presentation`   | views, сериализаторы, URL, компоненты, роутер      | бизнес-правила, запросы в БД |

Почему именно так:

* **Правила тестируются без фреймворка.** `backend/tests/test_domain.py` не просит фикстуру `db`
  и не поднимает Django — это обычные функции над обычными данными.
* **Замена инфраструктуры не трогает сценарии.** `AuthenticateUser` знает только о протоколах
  `UserRepository` и `PasswordHasher`; чем они окажутся — Postgres или заглушка в памяти —
  решается в одном файле, `backend/config/container.py`.
* **Границы видно в импортах.** Если в `domain` появился `from django...`, слой нарушен,
  и это видно в ревью без запуска кода.

Единственное место, где всё соединяется, — композиционный корень:
`backend/config/container.py` и `frontend/src/app/main.ts`.

## Аутентификация

Сессионные cookie, не токены: `HttpOnly`-cookie недоступна скриптам на странице, поэтому XSS не
уносит сессию — в отличие от JWT в `localStorage`.

1. SPA запрашивает `GET /api/v1/auth/csrf/` и получает cookie `csrftoken`.
2. Любой небезопасный запрос отправляет её обратно в заголовке `X-CSRFToken`.
3. nginx отдаёт SPA и API с одного origin, поэтому cookie — своя, CORS не нужен,
   а `SameSite=Lax` достаточно.

Что сделано намеренно:

* Неверный пароль, несуществующий адрес и адрес неправильного формата дают **один и тот же**
  ответ `400 invalid_credentials`. Разные ответы превратили бы форму входа в способ узнать,
  кто зарегистрирован.
* Для несуществующего адреса пароль всё равно хешируется (`dummy_verify`), чтобы ответ занимал
  столько же времени.
* `login()` вызывается только после успешной проверки — он меняет ключ сессии, и это то, что
  защищает от session fixation.
* `login`, `register` и `logout` помечены `csrf_protect` вручную: DRF считает `APIView`
  csrf-exempt и проверяет токен только для **уже аутентифицированных** запросов, то есть эти три
  эндпоинта без декоратора принимали бы межсайтовый POST.
* nginx ограничивает `login` и `register` до 10 запросов в минуту с адреса.

Любая ошибка API — доменная, DRF или неожиданная — выходит одним конвертом:

```json
{ "error": { "code": "invalid_credentials", "message": "…", "details": {} } }
```

`code` — стабильный машинный признак, по нему ветвится клиент; `message` — готовый текст для
пользователя. Трассировка никогда не попадает в ответ.

## Проверка

`pytest` и `ruff` есть только в образе, собранном с `INSTALL_DEV=1`, — его даёт
dev-наложение:

```bash
cd infra && docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build
docker compose exec backend python -m pytest -q
docker compose exec backend python -m ruff check /app
docker compose exec backend python manage.py makemigrations --check --dry-run

cd ../frontend && npm run build && npm test
cd .. && python3 scripts/eval.py --verbose
```

Текущее состояние: 190 тестов бэкенда и 23 фронтенда проходят, `ruff check` чист, сборка фронта
проходит полную проверку типов, `eval.py` даёт 100% / 100% / 100%.

Подробнее — [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).
