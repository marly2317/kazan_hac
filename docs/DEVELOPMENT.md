# Разработка

## Запуск

```bash
cp infra/.env.example infra/.env
python3 -c "import secrets; print(secrets.token_urlsafe(64))"   # в DJANGO_SECRET_KEY
```

Боевой стек:

```bash
cd infra && docker compose up --build
```

Стек для разработки — то же плюс dev-зависимости в образе и исходники, примонтированные в
контейнер:

```bash
cd infra && docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build
```

Разница ровно в двух вещах, см. комментарий в
[`infra/docker-compose.dev.yml`](../infra/docker-compose.dev.yml): сборка с `INSTALL_DEV=1`
(иначе `pytest` и `ruff` в контейнере просто отсутствуют) и bind-mount `../backend:/app`.
Боевой образ намеренно копирует код внутрь: контейнер, поведение которого зависит от
файловой системы хоста, — не артефакт поставки.

Приложение открывается на `http://localhost:${PUBLIC_PORT}` (по умолчанию 8080).
`SEED_DEMO_USER=1` создаёт `demo@example.com` / `demo-password-2026` — только для стенда.

> **gunicorn не перезагружается сам.** При смонтированных исходниках правка видна лишь после
> `docker compose restart backend`. Это первое, что стоит проверить, если изменение «не
> применилось».

## Проверка

Всё, что должно проходить перед тем, как считать правку готовой:

```bash
# бэкенд: 181 тест, большинство без базы
docker compose exec backend python -m pytest -q
docker compose exec backend python -m ruff check /app
docker compose exec backend python manage.py makemigrations --check --dry-run

# фронтенд: типы, сборка, 13 тестов
cd frontend && npm run build && npm test

# качество подбора на живом стенде
python3 scripts/eval.py --verbose
```

`scripts/eval.py` — главная проверка при любой правке алгоритма. Он печатает точность@1,
точность@5, долю верных воздержаний и время ответа и **возвращает ненулевой код**, если
сервис уверенно отвечает там, где правильного ответа нет. Эта ошибка — самая дорогая, и
проходить молча она не должна.

## Как тестируется алгоритм

Сценарий подбора зависит только от портов, поэтому тесты гоняют его на заглушках в памяти:
ни базы, ни HTTP, ни Django. `FakeCatalog` в `backend/tests/test_autofill.py` — это словарь
позиций со сходством и характеристиками; `FakeCorrector` возвращает заранее заданное
исправление.

```python
catalog = FakeCatalog({"A": ("Молоток", 3.0, [range_characteristic("Длина", "100", "500")])})
result = analyser(catalog).execute(AnalyzeDescriptionInput(description="молоток 9000 мм"))
```

Поэтому 181 тест выполняются за шесть секунд, и порог можно менять, сразу видя последствия.

| Файл | О чём |
| --- | --- |
| `tests/test_matching.py` | можно ли показывать кандидата как ответ |
| `tests/test_autofill.py` | извлечение, привязка чисел, сужение, воздержание, проверки |
| `tests/test_spellcheck.py` | что корректор исправляет и, главное, чего не трогает |
| `tests/test_units.py` | канонизация и перевод единиц |
| `tests/test_ktru.py` | парсер XML, границы диапазонов |
| `tests/test_catalog_api.py`, `test_auth_api.py` | HTTP-слой, нужна база |
| `frontend/tests/*.test.ts` | домен интерфейса и хранилище |

**Каждый тест в этих файлах написан по реальному наблюдённому дефекту, и комментарий над ним
объясняет, какому.** Прежде чем ослабить падающий тест, прочитайте комментарий: скорее всего,
он описывает случай, который уже один раз сломался.

## Правила, которые стоит соблюдать

* **Пороги живут в `domain` вместе с обоснованием.** Число без комментария, откуда оно
  взялось, через неделю никто не сможет изменить осознанно.
* **`domain` не импортирует Django.** Это проверяется глазами в ревью: `from django...` в
  доменном файле — нарушение слоя.
* **Конвейер исправления не должен портить правильный ввод.** Любое новое правило корректора
  сопровождается тестом «чего он не трогает», а не только «что он чинит».
* **Воздержание — это результат.** Если правка повышает точность за счёт того, что сервис
  начинает отвечать там, где ответа нет, это ухудшение.

## Переменные окружения

Полный список с комментариями — [`infra/.env.example`](../infra/.env.example). Существенное:

| Переменная | Значение |
| --- | --- |
| `DJANGO_SECRET_KEY`, `POSTGRES_PASSWORD` | обязательны |
| `PUBLIC_PORT` | порт, который публикует nginx |
| `CSRF_TRUSTED_ORIGINS` | со схемой и портом, иначе каждый POST падает на проверке CSRF |
| `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE` | `0` для HTTP локально, `1` сразу после TLS |
| `SEED_DEMO_USER`, `SEED_CATALOG` | демо-данные; в реальном развёртывании нельзя |
| `LLM_BASE_URL` | **пусто** — стадия отсутствует в конвейере; см. ниже |
| `COLLECT_REFERENCE_GAPS` | `1` — сбор наблюдений о нехватке в справочнике; `0` выключает |

### Пробелы в справочнике

Накопленное смотреть в админке: `/admin/` → **«пробелы в справочнике»**, отсортировано по
убыванию частоты. Строки пишет сервис, править можно только `status` и `note` — это журнал
наблюдений, а не справочник, и редактирование цифр сделало бы их недостоверными. Есть
групповые действия «принять в работу» и «отклонить», чтобы разобранное не возвращалось в
список.

Если таблица пуста, а наблюдения ожидались, причин обычно две: `COLLECT_REFERENCE_GAPS=0`
либо запросы шли без `settled=1` (разбор по мере ввода наблюдения не пишет — намеренно).
Правило и обоснование — [ALGORITHM.md](ALGORITHM.md#шаг-10-что-подсказать-тем-кто-ведёт-справочник).

### О стадии языковой модели

Код вендор-нейтрален: говорит на OpenAI-совместимом протоколе, не называет ни вендора, ни
модель, и при пустом `LLM_BASE_URL` просто не попадает в конвейер. Правила хакатона
запрещают внешние API проприетарных LLM и разрешают только **открытые** модели (суммарно
≤ 40 ГБ VRAM), в том числе через роутеры, с предпочтением отечественных.

**Сейчас выключено намеренно.** Стадия запускается последней — только когда раскладка и
словарь ничего не изменили, то есть на тексте, который детерминированные стадии признали
правильным. На замере она портила корректный ввод («Сталь» → «сталь») и добавляла около
1.1 с к каждому запросу при полном времени ответа 39 мс без неё. Скорость обработки —
отдельный критерий оценки.
