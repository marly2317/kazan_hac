# Подбор КТРУ по описанию товара — рассказ для защиты (ML-часть)

## 1. Задача одной фразой

Поставщик пишет товар своими словами («Шкаф детский деревянный, 3 секции») — система выдаёт
**конечный код КТРУ**, заполняет его характеристики с привязкой к тексту, задаёт уточняющие
вопросы, когда данных не хватает, и объясняет ошибки («5 м — вне диапазона 60–250 см»).

Охват: одежда (14), обувь и сумки (15.20, 15.12), мебель (31), инструмент (25.73, 28.24) —
**288 типов товара (семейств), 1502 конечных кода, 81 общая позиция**.

## 2. Ключевое наблюдение о данных — почему архитектура двухуровневая

В КТРУ конечные коды одного типа **называются одинаково** и различаются только значениями
характеристик:

| Код | Название | Различие |
| --- | --- | --- |
| 31.01.12.131-00000004 | Шкаф детский для одежды деревянный | секций: 1 |
| 31.01.12.131-00000007 | Шкаф детский для одежды деревянный | секций: 3 |
| 31.03.12.140-00000001 | Наматрасник … из пеноматериала | длина 1900–2400 мм |
| 31.03.12.140-00000004 | Наматрасник … из пеноматериала | длина 800–1200 мм |

Отсюда решение, на котором держится всё остальное:

1. **Тип товара (родительская позиция, «семейство») — задача поиска по тексту.**
2. **Конечный код (дочерняя позиция, «лист») — задача на характеристики**: текстом его не
   найти, его можно только **вычислить** по значениям, попадающим в интервалы КТРУ.

## 3. Как мы пришли к текущему решению (эволюция)

| Этап | Что пробовали | Что узнали |
| --- | --- | --- |
| 0 | Триграммы Postgres (pg_trgm) по наименованиям позиций | 93% на малом наборе, но ищет **строки**, а не тип; не понимает «болгарку»; растёт линейно с размером справочника |
| 1 | Полнотекстовый поиск Postgres (FTS) | хуже триграмм (57%): описание не обязано содержать слова наименования |
| 2 | OpenSearch (ветка команды) | тяжёлая инфраструктура ради ~300 документов; заменили собственным индексом |
| 3 | BM25 со стеммингом по **карточкам семейств** | @1 80% на реальных СТЕ: точные термины ловит, синонимы — нет |
| 4 | Векторы Qwen3-Embedding-0.6B | @1 85%: синонимы и перефразировки |
| 5 | **BM25 + векторы, слияние RRF** (вес вектора подобран) | **@1 89%, @5 96%** — лучший поиск, оставили |
| 6 | Реранкер Qwen3-Reranker-0.6B | в одиночку @1 83% (хуже поиска), с поиском — без прироста; на CPU 20–55 с. **Выключен** (код сохранён) |
| 7 | LLM для выбора типа на каждом запросе | медленно и дорого; оставили **только для неоднозначных** запросов, на топ-5 |
| 8 | LLM для извлечения характеристик | необходима: синонимы, свободный порядок, числа с единицами; но **с цитатами и проверкой кодом** |
| 9 | Gemma 4 26B → **Qwen3.6-35B-A3B** | MoE, 3B активных параметров — быстро; режим рассуждений выключен |
| 10 | Ограниченное декодирование JSON | Gemma зацикливалась; работаем «схема в промпте + проверка + 1 исправление» |

Принцип, который мы выдерживали: **каждое решение — по замеру**, а не по мнению. Там, где
замер показал, что сложная модель не лучше простой (реранкер), мы её выключили.

## 4. Текущая архитектура: что вызывается, где и зачем

### Офлайн (один раз, до запуска)

| Шаг | Что делаем | Зачем |
| --- | --- | --- |
| База знаний | XML КТРУ → только `all_actual`, статус ACTIVE, последняя версия → семейства и листья, интервалы чисел с единицами ОКЕИ | вся логика подбора опирается на точные данные КТРУ |
| Метаданные | синонимы и разговорные названия семейств («болгарка» → УШМ) | поиск по языку поставщика |
| Векторы | карточка каждого семейства → Qwen3-Embedding-0.6B | в работе кодируется только запрос |
| Статистика СТЕ | ~300 тыс. реальных СТЕ портала → что обычно указывают сверх КТРУ | подсказки для полноты карточки |

### Онлайн (на каждый запрос)

Важно различать два результата: после шагов 1–3 известен **тип товара** (родительская позиция,
семейство), а **конечный код** КТРУ появляется только на шаге 7 — его вычисляют по характеристикам.

```
текст
 │
 ├─[1] опечатки и раскладка (SymSpell по словарю КТРУ)
 │
 ├─[2] поиск типа товара: BM25 + векторы → слияние RRF → топ-10 семейств
 │
 ├─[3] выбор семейства
 │      ├─ поиск однозначен ───────────────► семейство (без LLM, ~50% запросов)
 │      └─ иначе: LLM-1 на топ-5 ──────────► семейство / вопрос «уточните тип» / «нет в КТРУ»
 │
 ├─[4] LLM-2: характеристики по схеме семейства + цитаты + бренд/модель
 │         + дополнительные (с подсказкой названий из статистики реальных СТЕ)
 │
 ├─[5] проверки кодом: цитаты, фильтр оценок, дубли доп. характеристик
 │
 ├─[6] нормализация значений: единицы ОКЕИ, интервалы, уверенность
 │
 ├─[7] сужение до конечного кода (листа)
 │      ├─ 1 лист  ──► код + карточка
 │      ├─ >1 листа ─► уточняющий вопрос (ответ кнопкой — без LLM)
 │      └─ 0 листов ─► объяснение ошибки и ближайшее допустимое значение
 │
 └─[8] карточка: значения с цитатами и интервалом КТРУ, что дозаполнить,
          «часто указывают в СТЕ этого типа», трассировка всех шагов
```

| # | Шаг | Чем | Сколько кандидатов / какие пороги | Почему так |
| --- | --- | --- | --- | --- |
| 1 | Опечатки, раскладка | SymSpell + раскладка, словарь **из самого КТРУ** | — | исправление всегда ведёт к слову справочника |
| 2 | Поиск типа товара | BM25 со стеммингом + Qwen3-Embedding-0.6B, слияние RRF: `1/(60+место BM25) + 0,6·1/(60+место вектора)` | ищем среди 288 семейств, берём **топ-10** | каждый метод ловит то, что пропускает другой; слияние лучше обоих |
| 3а | Быстрый путь | правило, без моделей | лидер **первый и в BM25, и в векторах**, **все слова его названия есть в запросе**, отрыв по **косинусу** от второго ≥ 0,03 (не по итоговому скору RRF) | где LLM ничего не добавит, она не вызывается; 0 ошибок на замере |
| 3б | LLM-1 | Qwen3.6-35B-A3B, рассуждение выключено | получает **топ-5** семейств + ближайшие общие позиции; возвращает каждому оценку 0–1 | лидер ≥ 0,75 и отрыв ≥ 0,2 → одно семейство; несколько близких → вопрос «уточните тип» (до 5 вариантов); все < 0,4 → «нет в КТРУ» |
| 4 | LLM-2 | та же модель, один вызов | схема **выбранного семейства**: все характеристики его листьев с допустимыми значениями; подсказка — названия типичных доп. характеристик из реальных СТЕ | извлечение — единственное место, где нужен язык |
| 5а | Проверки описания целиком | код | отрицательные значения («-750 мм»); несколько товаров в одной позиции («стол и стул»); два значения одной характеристики («прямой и угловой»); величина, которой у товара нет («2 кВт» у костюма); характеристика чужого товара («размер одежды» у пилы); значение, которого нет у выбранного кода; неправдоподобное количество | найдено на тестовом файле организаторов; ошибка объясняется, а не исчезает молча |
| 5 | Проверки | код | цитата обязана быть в тексте; оценки («афигенный») и общие поля («Описание») отбрасываются; доп. характеристика, дублирующая основную, бренд или модель, отбрасывается или переносится в основную | защита от выдумок и мусора |
| 6 | Нормализация | код | перевод единиц (2 м → 2000 мм), проверка размерности, сопоставление с допустимыми значениями, уверенное/слабое значение | числа и единицы LLM не доверяем |
| 7 | Сужение | код | каждое значение против каждого листа семейства | конечный код вычисляется, а не угадывается |
| 7а | Вопрос | код | характеристика с минимальным ожидаемым остатком `Σnᵢ²/N` | в среднем 2 вопроса, максимум 3 |
| 8 | Карточка | код | значения с цитатой и интервалом КТРУ; обязательные к дозаполнению; «часто указывают в СТЕ этого типа» (≥ 20% реальных карточек); трассировка шагов | объяснимость и полнота карточки |

После первого ответа: **ответ кнопкой** — только код (шаги 6–8), без LLM; **ответ текстом** —
мини-LLM-2 по одной характеристике, затем шаги 6–8.

**LLM вызывается 1–2 раза за запрос (LLM-1 — только в половине запросов) и никогда не выбирает
конечный код и не считает числа.**

Без LLM (нет ключа, сбой сети): шаг 3 — по поиску, при неуверенности вопрос «уточните тип»;
шаг 4 — правила (значения из словаря семейства, числа по слову-подсказке и единице).

### Сужение до конечного кода — подробнее

* уверенное значение (есть цитата, однозначно легло на КТРУ) несовместимо с листом →
  лист **исключён**;
* слабое значение несовместимо → лист **штрафуется** (×0,7), но остаётся: значение могло
  быть понято неверно;
* у листа нет характеристики → ×0,9;
* градации «≥0,25 / ≥0,35 / ≥0,5»: число 0,5 относится к самой узкой — «≥0,5»;
* не осталось ни одного листа → находим **минимальный набор значений-виновников** и для
  каждого ближайшее допустимое значение: так строится объяснение ошибки.

## 5. Как мы мерили качество

### Наборы данных

| Набор | Что это | Как размечен | Для чего |
| --- | --- | --- | --- |
| **Реальные наименования СТЕ** (46) | наименования из выгрузок портала | семейство по КТРУ, сверено вручную | поиск семейства — **главная, честная метрика** |
| **Тест-кейсы** (120) | синтетические описания поставщика по реальным СТЕ | эталонные семейство, код, ожидаемые вопросы и ошибки | весь конвейер |
| **Полный перебор листьев** (1421) | для каждого листа — «пользователь, знающий истинные характеристики» | эталон — сам лист | логика сужения и вопросов |

Тест-кейсы — **синтетика**: реальные СТЕ переписаны так, как пишет поставщик, по типам:

| Тип | Кол-во | Пример |
| --- | --- | --- |
| полное описание | 36 | «УШМ Уралмаш 1110/125, 1110 Вт, диск 125 мм, от сети» |
| короткое | 21 | «болгарка 230 мм» |
| разговорное | 15 | «углошлифовалка аккумуляторная 18В 125мм» |
| с ошибкой в значении | 12 | «Ранец школьный, высота 45 см» (вне диапазона) |
| демо-сценарии | 10 | сценарии из постановки |
| не хватает данных | 10 | «Электролобзик Graphite 400 Вт» |
| опечатки / раскладка | 8 | «,jkufhrf 125 vv» |
| товара нет в КТРУ | 8 | «Отвёртка крестовая PH2» |

**Честное ограничение.** Тест-кейсы составляли мы, и их формулировки пересекаются с
синонимами семейств, — метрика на них завышена. Поэтому для поиска главный ориентир —
**реальные наименования СТЕ**, которых система не «видела». Это и есть наш аргумент, почему
выбор между методами делали по ним.

### Результаты

| Что | Результат |
| --- | --- |
| Поиск семейства, реальные СТЕ: BM25 / векторы / **RRF** | @1: 80% / 85% / **89%**; RRF @5 96%, @30 98% |
| Семейство в конвейере с LLM (120 кейсов)* | 89% |
| Конечный код с LLM* | 76 из 88 (86%) |
| «Нет в КТРУ» с LLM* / без LLM | 6 из 9 / 0 из 9 |
| Достижимость конечных кодов вопросами | **1405 из 1421**; остальные 16 — пары, неразличимые в самом КТРУ |
| Вопросов до кода | медиана 2, максимум 3 |
| Быстрый путь без LLM (порог отрыва 0,03) | 57 из 119 запросов, **ошибок 0** |
| Время | без LLM ~1 с; с LLM ~3–6 с |

\* прогон на Gemma 4 до последних улучшений; на Qwen3.6 полный прогон не делали (платный).

Порог быстрого пути проверен перебором: при отрыве по косинусу 0 / 0,01 / 0,03 / 0,05 / 0,08 /
0,1 без LLM решается 63 / 60 / 57 / 54 / 46 / 36 запросов из 119, и **ни один не ошибочен** —
главное условие безопасности не отрыв, а «лидер первый в обоих поисках и его название целиком
в запросе». Порог 0,03 — запас: держит ноль ошибок и отдаёт LLM только половину запросов.

## 6. Почему именно такое решение — аргументы

1. **Двухуровневость следует из данных**: конечные коды различаются только
   характеристиками, значит код нужно вычислять, а не искать.
2. **Гибридный поиск** выбран замером: RRF лучше каждого метода по отдельности.
3. **LLM — только там, где нужен язык**: выбор типа в трудных случаях и извлечение значений.
   Код, интервалы, единицы, ошибки — детерминированный код: воспроизводимо и объяснимо.
4. **Каскад по стоимости**: половина запросов решается без LLM-1, ответы кнопками — вообще
   без LLM, ответы модели кэшируются.
5. **Защита от выдумок**: обязательная цитата из текста; проверка по допустимым значениям КТРУ;
   фильтр оценок («афигенный») и дублей в дополнительных характеристиках.
6. **Объяснимость**: в ответе трассировка — какой шаг, какая модель, сколько миллисекунд, что
   решено; у каждого значения — цитата и интервал КТРУ.
7. **Деградация без LLM**: поиск + правила + вопросы продолжают работать.

## 7. Ограничения и что дальше

* пороги уверенности LLM-1 эмпирические (подобраны на тест-кейсах), не откалиброваны;
* реранкер помогает только на GPU и по замеру не дал прироста — включается настройкой;
* полный прогон качества на Qwen3.6 не сделан;
* статистика из реальных СТЕ — подсказка, значения не подставляются без текста или
  пользователя.
