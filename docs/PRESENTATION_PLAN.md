# Презентация: техническое задание для генерации слайдов

> Этот файл — готовый промпт для генератора слайдов. Всё, что ниже, — содержание и раскладка.
> Тексты в «кавычках-ёлочках» и таблицы переносить на слайд дословно.

## Общие требования

* **Формат:** 16:9, 14 слайдов основной части + 6 запасных. Выступление — 7 минут
  (≈ 30 секунд на слайд), затем 10 минут вопросов жюри.
* **Аудитория:** заказчики (Портал поставщиков, Департамент города Москвы), не ML-инженеры.
  Язык — простой, через пользу для поставщика. Технические названия — мелко, вторым планом.
* **Стиль:** цвета Портала поставщиков — белый фон, красный акцент (#DB2B21 или близкий),
  тёмно-серый текст, светло-серые плашки. Шрифт без засечек (Montserrat / Inter).
  Минимум текста: заголовок-вывод + одна визуализация + не больше 3 коротких строк.
* **Заголовок каждого слайда — вывод**, а не тема («Код вычисляется по характеристикам»,
  а не «Сужение»).
* **Единые термины на всех слайдах:**
  * **тип товара** — родительская позиция КТРУ («Шкаф детский для одежды деревянный»);
  * **конечный код** — конечная позиция КТРУ (31.01.12.131-00000007);
  * **карточка СТЕ** — карточка товара на портале;
  * **языковая модель** — Qwen3.6-35B-A3B.
* **Примеры** — моноширинным шрифтом в плашках «было → стало». Все примеры ниже реальные:
  система их действительно так обрабатывает.
* **Нумерация** слайдов внизу справа; логотип решения — вверху слева на всех слайдах кроме
  титульного.

## ОСНОВНАЯ ЧАСТЬ

### Слайд 1. Титул
* Название решения: **«Автозаполнение СТЕ по описанию товара»**.
* Подзаголовок: «Поставщик пишет товар своими словами — получает код КТРУ и заполненную карточку».
* Внизу мелко: «Tender Hack · Казань · 2026».
* Визуал: справа — стилизованная карточка товара, в которой поля заполняются сами
  (иллюстрация, без реальных данных).

### Слайд 2. Заполнение карточки отнимает у поставщика время и ведёт к ошибкам
* Три плашки-проблемы с иконками:
  1. «Найти код: тысячи позиций КТРУ с одинаковыми названиями»
  2. «Заполнить характеристики: десятки полей в точных формулировках и единицах справочника»
  3. «Ошибиться легко: не та единица, недопустимое значение, не тот код → карточку отклоняют»
* Внизу крупно одна фраза: «Поставщик хочет тратить меньше времени и сил на оформление».
* Визуал: слева — схематичная пустая форма с множеством полей и выпадающим деревом КТРУ.

### Слайд 3. Решение: описал своими словами — получил готовую карточку
* Слева — поле ввода с текстом:
  `Прямой раскладной диван на деревянном каркасе, 3 посадочных места`
* Стрелка вправо → результат (скриншот интерфейса или его макет):
  код `31.09.12.110-00000005`, характеристики с отметкой «из текста», блок «дозаполнить».
* Справа — пять пунктов с иконками (что делает система):
  1. **Понимает** описание — в любой форме, с опечатками
  2. **Находит** конечный код КТРУ
  3. **Заполняет** характеристики и приводит единицы к справочнику
  4. **Подсказывает**, что ещё заполнить
  5. **Предупреждает** об ошибках — с объяснением, что исправить

### Слайд 4. Ключевая идея: коды одного типа отличаются только характеристиками
* Таблица (реальные данные КТРУ):

  | Конечный код | Название | Количество секций |
  | --- | --- | --- |
  | 31.01.12.131-00000004 | Шкаф детский для одежды деревянный | 1 |
  | 31.01.12.131-00000008 | Шкаф детский для одежды деревянный | 2 |
  | 31.01.12.131-00000007 | Шкаф детский для одежды деревянный | 3 |
  | 31.01.12.131-00000006 | Шкаф детский для одежды деревянный | 4 |
  | 31.01.12.131-00000005 | Шкаф детский для одежды деревянный | ≥ 5 |

  Столбец «Название» — одинаковый серым; столбец «Количество секций» выделен красным.
* Под таблицей — вывод в две плашки со стрелкой между ними:
  **Этап 1. Найти тип товара** — по смыслу описания →
  **Этап 2. Вычислить конечный код** — по значениям характеристик
* Подпись мелко: «Текстом конечный код не найти — его можно только вычислить».

### Слайд 5. Как работает решение — 6 шагов
Горизонтальная лента из 6 блоков со стрелками. Под каждым блоком — одна строка «чем».
Блоки 3 и 4 обвести пунктиром с подписью «Этап 1» и «Этап 2»; языковую модель отметить
значком ✦ только на двух блоках.

| # | Блок | Подпись под блоком |
| --- | --- | --- |
| 1 | Исправление опечаток | словарь КТРУ |
| 2 | Поиск типа товара | поиск по словам и по смыслу |
| 3 | Выбор типа | правила; ✦ модель — только в спорных случаях |
| 4 | Извлечение характеристик | ✦ языковая модель + цитаты из текста |
| 5 | Проверка по КТРУ и сужение до кода | справочник КТРУ, правила |
| 6 | Карточка, ошибки, подсказки | справочник КТРУ + статистика 300 тыс. СТЕ |

* Внизу плашка: «Модель — только там, где нужно понимать язык. Код, единицы и проверки —
  строгие правила по справочнику: результат воспроизводим и объясним».

### Слайд 6. Схема реализации (BPMN)
* BPMN-диаграмма с 4 дорожками (pools/lanes):
  1. **Поставщик** — «Ввести описание» → (позже) «Ответить на вопрос» / «Выбрать тип» /
     «Дозаполнить характеристики» → «Получить карточку».
  2. **Сервис подбора** — «Исправить опечатки» → «Найти тип товара» →
     шлюз «Тип однозначен?» (да → дальше; нет → задача модели) → «Извлечь характеристики» →
     «Проверить по КТРУ, привести единицы» → «Сузить до кода» →
     шлюз «Сколько кодов?» (1 → «Сформировать карточку»; >1 → «Задать вопрос»;
     0 → «Объяснить ошибку») → «Проверить описание на ошибки» → «Показать результат».
  3. **Языковая модель** — «Выбрать тип из 5 вариантов / ответить "нет в КТРУ"»,
     «Извлечь значения с цитатами».
  4. **Справочник КТРУ и статистика СТЕ** — хранилища данных (data store), к ним пунктирные
     связи от задач поиска, проверки и подсказок.
* Возврат от «Ответить на вопрос» к «Сузить до кода» — цикл (ответ кнопкой, без модели).

### Слайд 7. Шаг 1–3: понимаем описание и находим тип товара
* Блок «Исправление опечаток и раскладки» — три плашки «было → стало»:
  * `,jkufhrf 125 vv jn ctnb` → `болгарка 125 мм от сети`
  * `шуруповрет` → `шуруповёрт`
  * `сабелька аккумуляторная` → `сабельная пила`
* Блок «Поиск типа товара»:
  * «Ищем среди 288 типов товара одновременно по словам и по смыслу — и объединяем результаты».
  * «Понимаем разговорные названия: „болгарка“ → углошлифовальная машина».
* Блок «Решение» — развилка из двух стрелок:
  * «Тип назван однозначно → берём сразу (≈ половина запросов, 0 ошибок на тестах)»
  * «Спорный случай → языковая модель выбирает из 5 лучших или честно отвечает
    „такого товара нет в КТРУ“»

### Слайд 8. Шаг 4: извлекаем характеристики — каждое значение подтверждено текстом
* Слева — исходный текст с подсветкой фрагментов (каждый фрагмент своим цветом):
  `Наматрасник противопролежневый с пенополиуретановым наполнителем, длина 2 м, ширина 90 см`
* Справа — карточка, строки связаны линиями с подсвеченными фрагментами:

  | Характеристика | Значение | По КТРУ | Источник |
  | --- | --- | --- | --- |
  | Длина | 2000 мм | ≥1900 ≤2400 мм | «длина 2 м» |
  | Ширина | 900 мм | ≥600 ≤1900 мм | «ширина 90 см» |

* Внизу две строки:
  * «Тип товара известен → известен список его характеристик и допустимых значений из КТРУ».
  * «Значение без цитаты из текста не принимается — модель не может „придумать“ характеристику».

### Слайд 9. Значения и единицы приводятся к справочнику КТРУ
* Сетка из 4 плашек «написал поставщик → в карточке»:
  * `2 м 15 см` → `2150 мм`
  * `90 см` → `900 мм` (в КТРУ длина в миллиметрах)
  * `деревянном каркасе` → `Тип каркаса: Деревянный`
  * `свинцовый эквивалент 0,3 мм Pb` → градация КТРУ `≥ 0,25 мм`
* Подпись: «Единицы — по классификатору ОКЕИ; размерность проверяется: длину не сравниваем
  с массой».

### Слайд 10. Шаг 5: код вычисляется — каждое значение отсекает лишние коды
* Воронка сверху вниз (реальный пример — наматрасник):
  `288 типов товара` → `Наматрасник противопролежневый из пеноматериала: 4 кода` →
  `длина 2000 мм: 1 код` → **`31.03.12.140-00000001`**
* Справа — блок «Если данных не хватает»:
  * «Задаём **один** вопрос — тот, что сильнее всего сокращает выбор»
  * «Варианты — кнопками из КТРУ; ответ кнопкой обрабатывается мгновенно»
  * «В среднем 2 вопроса, максимум 3»
* Внизу крупная цифра: **«1405 из 1421 конечного кода достижимы»** —
  мелко: «остальные 16 — пары кодов, которые в самом КТРУ ничем не различаются».

### Слайд 11. Ошибки находим и объясняем, а не исправляем молча
* Таблица на весь слайд (реальные примеры из тестового файла организаторов):

  | Описание поставщика | Что сообщает система |
  | --- | --- |
  | Стол обеденный, высота **-750 мм** | Отрицательное значение невозможно |
  | Матрац, длина **5 м** | Вне диапазона КТРУ 60–250 см → ближайшее 250 см |
  | Диван **прямой и угловой** одновременно | У характеристики может быть одно значение |
  | **Стол и стул** в одной позиции | В позиции несколько товаров — выберите один |
  | Спортивный костюм, **мощность 2 кВт** | Характеристика не относится к товару |
  | Сабельная пила, **размер одежды 52** | Характеристика другого товара |
  | Сетевая дрель, **аккумулятор 4 Ач** | Нет у выбранного кода — проверьте описание |

* Цветовые метки слева от строк: красная — ошибка, жёлтая — предупреждение.
* Подпись: «Каждое сообщение — причина + конкретный шаг: замените, уберите или выберите».

### Слайд 12. Подсказываем, что ещё заполнить — по КТРУ и по практике портала
Три колонки-источника:
1. **Справочник КТРУ** — «Обязательные характеристики, которых нет в описании → „дозаполнить“,
   варианты кнопками».
2. **Описание поставщика** — «Свойства сверх КТРУ → дополнительные характеристики»
   * пример: `Принт: пони` ✓ · `Описание: афигенный` ✗ (оценка, не свойство — отброшено)
   * «Дубли основных характеристик, бренда и модели убираются».
3. **300 тысяч реальных СТЕ** — «Посчитали, что обычно указывают у каждого типа товара»
   * пример: «Шуруповёрт: напряжение аккумулятора — в 78% карточек → предложим указать»
   * «Нетипичное для товара помечаем: проверьте, нужно ли».
* Внизу — мини-таблица сравнения как в интерфейсе:

  | Характеристика | В реальных СТЕ | У вас |
  | --- | --- | --- |
  | Количество скоростей | 95% | стоит указать: `1` `2` |
  | Напряжение аккумулятора | 78% | ✓ 18 В |

### Слайд 13. Качество измерено на реальных и проблемных описаниях
* Слева — «Как проверяли» (4 строки с иконками):
  * «Реальные наименования товаров с портала»
  * «120 описаний „как пишет поставщик“: полные, короткие, разговорные, с опечатками,
    с ошибками в значениях, товары вне КТРУ»
  * «Полный перебор всех 1421 конечного кода»
  * «Тестовый файл организаторов: 45 описаний, из них 15 „ловушек“»
* Справа — 4 крупные плитки-цифры:
  * **89%** — тип товара определён верно (в 5 лучших вариантах — **96%**)
  * **86%** — верный конечный код
  * **99%** — конечных кодов достижимы уточнениями
  * **0** — ошибок в решениях, принятых без модели
* Внизу — мини-график «как росло качество поиска типа (верный тип на 1-м месте)»:
  `поиск по словам 80%` → `поиск по смыслу 85%` → `вместе 89%`
  + подпись «плюс синонимы и разговорные названия для всех 288 типов».

### Слайд 14. Быстро, на открытых моделях, в рамках ограничений
* Три колонки:
  1. **Скорость** — «≈ 1 с без модели · 3–6 с с моделью · ответ кнопкой — мгновенно».
     «Модель вызывается только при необходимости: в половине запросов тип определяется без неё».
  2. **Модели** — «Только открытые: Qwen3-Embedding-0.6B (поиск по смыслу) и
     Qwen3.6-35B-A3B (смесь экспертов, 3 млрд активных параметров — быстрая).
     Через российского провайдера (Selectel). Укладываются в лимит 40 ГБ видеопамяти».
  3. **Надёжность и масштабирование** — «Без модели система продолжает работать: поиск + правила
     + вопросы». «Новая категория КТРУ — пересборка базы одной командой».
* Внизу итоговая строка: «Поставщик тратит минуты вместо часов, портал получает единообразные
  карточки».

## ЗАПАСНЫЕ СЛАЙДЫ (для вопросов жюри)

### Запасной A. Как развивалось решение — каждый шаг по замеру
Вертикальная лента «пробовали → результат → решение»:
| Пробовали | Что показал замер | Решение |
| --- | --- | --- |
| Триграммы в базе данных | ищут строки, а не тип; не понимают «болгарку» | отказались |
| Полнотекстовый поиск | хуже триграмм: описание не содержит слов названия | отказались |
| OpenSearch | тяжёлая инфраструктура ради 300 документов | заменили своим индексом |
| Поиск по словам (BM25) | 80% | оставили как часть |
| Поиск по смыслу (векторы) | 85% | оставили как часть |
| Слияние двух поисков | **89%** | ✓ в решении |
| Реранкер | не дал прироста, медленный | выключен (сохранён) |
| Модель на каждом запросе | медленно и дорого | только в спорных случаях ✓ |
| Модель выбирает код сама | невоспроизводимо, необъяснимо | код вычисляют правила ✓ |
| Строгий формат ответа модели | модель зацикливалась | проверка ответа кодом ✓ |

### Запасной B. Метаданные типов товара
* «Для каждого из 288 типов — синонимы и разговорные названия: „болгарка“, „сабелька“,
  „шуруповёрт“ → точное название КТРУ».
* «Используются поиском по словам и по смыслу — поставщику не нужно знать формулировки КТРУ».

### Запасной C. Почему модель не выбирает код
* «Модель понимает язык, но может ошибиться в числах и интервалах».
* «Код, единицы, интервалы и проверки — правила по справочнику: один и тот же ввод → один и тот
  же результат, каждое решение объяснено».

### Запасной D. Статистика реальных СТЕ — как посчитана
* «~300 тыс. карточек портала → привязали к типу товара по названию (только уверенно) →
  69 тыс. карточек, 166 типов товара».
* «Для каждого типа — доля карточек с каждой характеристикой сверх КТРУ и частые значения;
  показываем от 20% карточек».

### Запасной F. Ограничения и развитие
