# ML-модуль подбора КТРУ и автозаполнения характеристик СТЕ — архитектура

> TenderHack, кейс «Автозаполнение ключевых характеристик в СТЕ» (Портал поставщиков).
> Документ описывает **только ML/алгоритмическую часть**: от исправленного текста до итогового кода КТРУ и карточки характеристик.
> Исправление опечаток, модуль ошибок, UI и BPMN — вне этого документа (интерфейсы с ними описаны в §8).

---

## 0. Что делает модуль (в одном абзаце)

Пользователь вводит свободный текст о товаре (одежда, мебель, инструменты). Модуль:
1) определяет **семейство КТРУ** (тип товара) — LLM выбирает из полного списка семейств;
2) раскладывает текст **по схеме характеристик этого семейства** — LLM с ограниченным декодированием (JSON-схема с `enum` допустимых значений);
3) кодом нормализует значения и единицы, **сужает конечные позиции** семейства до одной;
4) если кодов несколько — задаёт **уточняющий вопрос** по самой информативной характеристике;
5) собирает **карточку СТЕ**: унифицированные характеристики КТРУ (с источником значения), дополнительные характеристики, бренд/модель, сигналы для модуля ошибок.

Онлайн — **2 вызова LLM**. Всё остальное — код и словари. Модели не дообучаются; качество обеспечивают структура КТРУ, словари и ограниченное декодирование.

## 1. Данные и ключевые факты (проверено на выгрузке)

### 1.1 Источники
| Источник | Что берём | Как |
|---|---|---|
| Выгрузка КТРУ (zip с вложенными zip) | Только файлы `nsiKTRUNew_all_actual_*.xml` (82 шт.), файлы `all_not-actual` (101 шт.) игнорируем. Только позиции `status = ACTIVE` | `parse_ktru.py` → SQLite (`positions`, `chars`, `vals`) |
| Описание структуры XML (docx, стр. 133) | Семантика полей `type`, `kind`, `isRequired`, `minMathNotation`/`maxMathNotation` и т.д. | справочно |
| Выгрузки товаров СТЕ с сайта (xlsx: инструменты; ещё 2 таблицы — одежда, мебель) | Название, модель, производитель, страна, характеристики строкой `Имя значение ед | …` | словари + тестовые кейсы (§3.10, §3.11) |
| Лист 2 xlsx «типовые характеристики категорий» (только инструменты, КПГЗ 01.11.02) | Типовые названия характеристик и единицы | унификация дополнительных характеристик (§4.7) |

### 1.2 Область (scope) — конфигурируемый список префиксов ОКПД2
```
SCOPE_OKPD2 = ["14.", "31.", "25.73", "28.24"]   # одежда, мебель, инструменты
```
Список вынести в конфиг (возможно расширение: 26.51.33 рулетки, 32.91.19 кисти малярные, 25.93.15 электроды, 15.20 обувь).

### 1.3 Цифры по scope
| | Одежда (14) | Мебель (31) | Инструменты (25.73, 28.24) | Всего |
|---|---|---|---|---|
| Активных позиций | 879 | 355 | 252 | **1486** |
| Семейств (корней) | 185 | 105 | 80 | **370** |
| из них услуги («Услуги по производству…») | 17 | 8 | 4 | 29 |
| из них общие без характеристик («…прочий») | 62 | 3 | 13 | 78 |
| **Конкретных семейств** (участвуют в выборе) | | | | **263** |
| Конечных позиций (листьев) | 795 | 263 | 191 | 1249 |
| Характеристик у листа, медиана | 3 | 7 | 5 | |

- Глубина дерева везде = 1 (родитель → дети). Детей у детей нет.
- `noNewFeatures = true` не встречается → дополнительные характеристики разрешены всегда.

### 1.4 Термины (используем ровно эти)
| Термин | Определение в данных |
|---|---|
| **Позиция** | запись КТРУ (`code`) со статусом ACTIVE |
| **Укрупнённая позиция (шаблон)** | `isTemplate = true`; содержит все допустимые значения характеристик семейства |
| **Семейство** | корневая позиция (без `parentPositionInfo`) + все позиции, у которых `parentPositionInfo.code` = её код. Одиночная позиция без детей = семейство из одной позиции |
| **Конечная позиция (лист)** | позиция, **у которой нет активных дочерних**. Только её код — итоговый ответ |
| **Общая позиция** | корень без характеристик («Инструмент ручной прочий», «Мебель прочая») — запасной вариант |
| **Услуга** | имя начинается с «Услуги» — исключаем из выбора |

### 1.5 Характеристика КТРУ
| Поле | Значения |
|---|---|
| `type` | 1 — качественная (текст), 2 — количественная (число) |
| `kind` | **1** — неизменяемая заказчиком: у листа **одно фиксированное** значение → **определяет, какой это лист**; **2** — выбор одного значения из списка; **3** — выбор нескольких |
| `isRequired` | обязательная или нет |
| `values` | ровно один из вариантов: `qualityDescription` (текст) · `rangeSet` (`minMathNotation`/`min`, `maxMathNotation`/`max` + ОКЕИ) · `valueSet/concreteValue` (+ ОКЕИ) |

Знаки границ: `greater` (>), `greaterOrEqual` (≥), `less` (<), `lessOrEqual` (≤). Граница может отсутствовать (открытый интервал). Типичный интервал: `≥a <b`.

### 1.6 Два типа семейств
- **«Вид + выбор»** (инструменты, мебель): листья различаются 1–2 характеристиками `kind=1`, остальное — `kind=2/3` со списками, которые **заполняются из текста**. Списки `kind=2` у разных листьев тоже могут отличаться (например, диапазоны мощности).
  - *Шлифмашина* (`28.24.11.000-00000042`): 8 листьев, `kind=1` «Вид» (Углошлифовальная машина / Эксцентриковая / Ленточношлифовальная …), ~15 характеристик `kind=2` (Мощность, Диаметр диска, Тип питания, Количество оборотов…).
  - *Шуруповерт*, *Дрель ручная электрическая*: листья различаются `kind=1` «Тип питания».
  - *Стол письменный* (`31.01.10.000-00000006`): `kind=1` «Тип каркаса» (Металлический / Деревянный) + 19 характеристик `kind=2/3`.
- **«Декартово произведение»** (одежда): листья = все комбинации значений `kind=1`.
  - *Одежда специальная для защиты от пониженных температур*: Класс защиты (4) × Вид одежды (14) × Пол (2) = 112 листьев, по 3 характеристики.

### 1.7 Единицы ОКЕИ в scope (код — название — сколько значений)
`003` Миллиметр 7896 · `004` Сантиметр 3758 · `796` Штука 1845 · `166` Килограмм 644 · `212` Ватт 558 · `006` Метр 117 · `331` Оборот в минуту 117 · `050` Квадратный миллиметр 106 · `263` Ампер-час 98 · `222` Вольт 78 · `039` Дюйм 72 · `280` Градус Цельсия 50 · `008` Километр 24 · `163` Грамм 18 · `598` Кубический метр в час 14 · `2355` Градус (плоского угла) 10 · `355` Минута 8.

Числовые характеристики **без ОКЕИ**: (а) единица в названии — «Скорость движения ленты, м/мин», «Максимальный крутящий момент (Нм)», «Производительность, г/мин»; (б) безразмерные — «Российский размер», «Рост», «Размер», «Количество оборотов в минуту», «Количество секций».

## 2. Общая схема

```
ОФЛАЙН (один раз, при сборке)
 XML ─► парсинг ─► роли позиций ─► нормализация значений/единиц ─► сигнатуры листьев
                                   │                                │
                                   ├─► JSON-схемы семейств           ├─► различающие характеристики
                                   ├─► карточки семейств ◄── LLM-метаданные (синонимы, описание)
                                   └─► индекс (BM25 + эмбеддинги)
 Выгрузки СТЕ ─► словари (единицы, бренды, названия характеристик, значения) ─► тест-кейсы

ОНЛАЙН (на каждый запрос)
 исправленный текст
   ├─[0] предпросмотр: поиск по индексу → топ-5 семейств (мгновенно, для UI)
   ├─[1] LLM-1: выбор семейства из ПОЛНОГО списка 263 карточек
   ├─[2] если «ничего не подходит» → просим уточнить товар/характеристики
   ├─[3] LLM-2: разложить текст по JSON-схеме семейства (enum, статус, цитата)
   ├─[4] код: проверка цитат, разбор единиц, перевод, попадание в интервалы
   ├─[5] код: сужение листьев семейства
   ├─[6] код: решение — код / вопрос / дозаполнить / конфликт
   └─[7] код: карточка СТЕ + сигналы для модуля ошибок
 ответ на вопрос кнопкой → сразу [5] (без LLM); свободным текстом → мини-LLM-2 → [4]
```

## 3. Офлайн-подготовка

Результат офлайна — набор файлов/таблиц, которые онлайн-часть грузит в память при старте. Пересборка — одной командой (`make build` / `python -m build_kb`).

### 3.1 Парсинг XML → SQLite
Уже реализовано: `parse_ktru.py` (потоковый `iterparse`, вложенные zip). Требования:
- брать только `all_actual` файлы и `status = ACTIVE` (код позиции уникален);
- таблицы:
  - `positions(code, version, name, okpd2, okpd2_name, is_template, parent, no_new, n_chars, okeis, descr)`
  - `chars(code, idx, ch_code, name, type, kind, required, actual, n_vals)`
  - `vals(code, idx, text, okei_code, okei, minop, min, maxop, max, concrete, fmt)`
- фильтр scope по `SCOPE_OKPD2`. Готовая база по scope: `ktru_3cat.sqlite`.

### 3.2 Роли позиций и семейства
Для каждой позиции вычислить:
```
family_id   = parent or code
role        ∈ {template, leaf, standalone_leaf, generic, service}
is_leaf     = нет активных детей
```
- `service`: имя начинается с «Услуги» → исключить из всего онлайна;
- `generic`: корень с `n_chars = 0` (не услуга) → не показывать в LLM-1 как обычное семейство, а отдельным списком «общие позиции» (§4.2);
- шаблон без детей → считается листом.

### 3.3 Нормализация значений и единиц
**Таблица единиц** `units`:
```

004 | Сантиметр | length | mm | 10    | см, сантиметр, cm
006 | Метр      | length | mm | 1000  | м, метр, m
008 | Километр  | length | mm | 1e6   | км
039 | Дюйм      | length | mm | 25.4  | дюйм, ", inch, ''
163 | Грамм     | mass   | kg | 0.001 | г, гр, грамм, g
166 | Килограмм | mass   | kg | 1     | кг, килограмм, kg
212 | Ватт      | power  | W  | 1     | вт, ватт, w;  (квт → factor 1000)
222 | Вольт     | voltage| V  | 1     | в, вольт, v

331 | Оборот в минуту | rpm | rpm | 1 | об/мин, оборотов в минуту, rpm
```

Синонимы пополнить из выгрузок СТЕ (§3.10). Для каждого значения `vals` сохранить также `min_base`, `max_base`, `concrete_base`.

**Единица в названии характеристики** (нет ОКЕИ): извлечь регуляркой из хвоста названия — после запятой (`, м/мин`) или в скобках (`(Нм)`), сопоставить со словарём единиц (добавить в словарь: `м/мин`, `Нм`/`Н·м`, `г/мин`, `л/мин`, `мм Pb`). Если единицы нет — характеристика безразмерная.

### 3.4 Сигнатура конечной позиции
Для каждого листа:
```json
{
  "code": "28.24.11.000-00000036",
  "family_id": "28.24.11.000-00000042",
  "chars": {
    "<char_key>": {
      "name": "Вид", "type": 1, "kind": 1, "required": true,
      "unit": null,
      "allowed": [ {"text": "Углошлифовальная машина"} ]                       // текст
      // или: [ {"min": 115, "min_inc": true, "max": 125, "max_inc": false, "okei": "003"} ]
      // или: [ {"concrete": 2, "okei": "796"} ]
    }
  }
}
```
`char_key` — нормализованное имя характеристики внутри семейства (lowercase, без лишних пробелов). Одно и то же имя у разных листьев семейства = одна характеристика.

### 3.5 Различающие характеристики семейства
Характеристика **различает** листья, если её набор `allowed` не одинаков у всех листьев семейства (или у части листьев её нет). Сохранить список `differentiators` для семейства — используется в карточке (§3.7) и при выборе вопроса (§4.6).

### 3.6 JSON-схема семейства (для LLM-2)
Строится из шаблона (или объединения характеристик всех листьев, если шаблона нет). Ключи — короткие id `c01…cNN` (маппинг id→имя кладём в промпт), чтобы не зависеть от кириллицы в ключах.
```json
{
  "type": "object",
  "properties": {
    "characteristics": {
      "type": "object",
      "properties": {
        "c01": {                                 // Вид (type=1, kind=1)
          "type": "object",
          "properties": {
            "status": {"enum": ["указано", "не указано", "противоречие"]},
            "value":  {"enum": ["Углошлифовальная машина", "Эксцентриковая (орбитальная)", "...", null]},
            "quote":  {"type": ["string", "null"]}
          },
          "required": ["status", "value", "quote"]
        },
        "c02": {                                 // Мощность (type=2)
          "type": "object",
          "properties": {
            "status": {"enum": ["указано", "не указано", "противоречие"]},
            "value":  {"type": ["number", "null"]},
            "unit":   {"type": ["string", "null"]},
            "quote":  {"type": ["string", "null"]}
          },
          "required": ["status", "value", "unit", "quote"]
        },
        "c03": {                                 // kind=3 (несколько значений)
          "type": "object",
          "properties": {
            "status": {"enum": ["указано", "не указано", "противоречие"]},
            "value":  {"type": "array", "items": {"enum": ["Полка для системного блока", "..."]}},
            "quote":  {"type": ["string", "null"]}
          },
          "required": ["status", "value", "quote"]
        }
      },
      "required": ["c01", "c02", "c03"]
    },
    "extra": {
      "type": "array",
      "items": {"type": "object",
                "properties": {"name": {"type": "string"}, "value": {"type": "string"},
                               "unit": {"type": ["string", "null"]}, "quote": {"type": "string"}},
                "required": ["name", "value", "unit", "quote"]}
    },
    "brand": {"type": ["string", "null"]},
    "model": {"type": ["string", "null"]}
  },
  "required": ["characteristics", "extra", "brand", "model"]
}
```
- Для **качественных** — `enum` = объединение допустимых значений по семейству.
- Для **числовых** — модель возвращает **число и единицу как в тексте**; в интервал кладёт код (§4.4). Интервалы в `enum` модели НЕ даём.
- Числовые с одним фиксированным набором конкретных значений (`concrete`) — тоже числом.

### 3.7 LLM-метаданные семейств (офлайн, через LLM)
263 конкретных семейства — генерация дешёвая (локальная модель или роутер, ~263 вызова или батчи по 10).
Для каждого семейства LLM получает: название, название ОКПД2, описание (`descr`, если есть), значения различающих `kind=1` (до 30 шт.), названия характеристик. Возвращает JSON:
```json
{
  "synonyms": ["болгарка", "УШМ", "углошлифовалка", "шлифовальная машинка", "..."],
  "description": "Ручной электроинструмент для шлифования, резки и зачистки поверхностей.",
  "keywords": ["шлифование", "диск", "абразив"]
}
```
Правила промпта: синонимы — **только названия типа товара** (разговорные, профессиональные, сокращения), 5–15 шт., без брендов и моделей; описание — 1–2 предложения; на русском. Результат сохранить в `family_meta` и **просмотреть глазами** (263 записи, ~30 минут), исправить явные ошибки.

### 3.8 Карточка семейства
Текстовое представление, одно и то же для индекса и для промпта LLM-1:
```
[F042] Шлифмашина
  синонимы: болгарка, УШМ, углошлифовалка, шлифовальная машинка, …
  что это: ручной электроинструмент для шлифования, резки и зачистки поверхностей
  ОКПД2: 28.24.11 Инструменты ручные электрические
  виды: Углошлифовальная машина; Эксцентриковая (орбитальная); Ленточношлифовальная …
  характеристики: Мощность, Диаметр диска, Тип питания, Количество оборотов в минуту, …
```
Для промпта LLM-1 — короткая версия (id, название, синонимы, ОКПД2-группа, «виды» до 10 значений), ~25–40 токенов на семейство → ~7–10 тыс. токенов на весь список.

### 3.9 Индекс (для предпросмотра и масштабирования)
- Документ = карточка семейства (§3.8, полная).
- **BM25** с русским стеммингом + **эмбеддинги** `qwen3-embedding:0.6b` (Ollama, локально).
  - запрос кодируется с инструкцией: `Instruct: Найди тип товара в каталоге КТРУ по описанию поставщика\nQuery: <текст>`; документы — без инструкции;
  - объединение результатов — RRF.
- Хранилище: OpenSearch (BM25 + `knn_vector` с заранее посчитанными векторами) **или** in-memory (rank_bm25 + numpy) — при 263 документах качество одинаковое; выбрать то, что быстрее поднять.
- Перед поиском из запроса **правилами** убираются числа с единицами, бренд и модель (словарь брендов §3.10).

### 3.10 Словари (из выгрузок СТЕ и КТРУ)
Модель не дообучается — словари критичны.
| Словарь | Источник | Как строим | Где используется |
|---|---|---|---|
| **Единицы** (синоним → ОКЕИ, множитель) | ОКЕИ из КТРУ + все единицы из строк характеристик СТЕ (`Вес 2.03 кг`, `об/мин`, `Н·м`, `Ач`) | regex «число + хвост» по всем строкам СТЕ → частотный список хвостов → ручное сопоставление с ОКЕИ | §4.4 |
| **Бренды** | колонка «Производитель» (+ латиница из «Модель») | уникальные значения, нормализация регистра | очистка запроса для поиска (§3.9), поле `brand` |
| **Названия характеристик** (СТЕ → КТРУ) | названия характеристик СТЕ (их ~11,6 тыс. вариантов в инструментах) и характеристики КТРУ/Лист 2 | эмбеддинги + косинус ≥ порога → кандидаты → быстрая ручная проверка топ-200 | унификация `extra` (§4.7) |
| **Значения** (синоним → значение КТРУ) | частые значения СТЕ («сетевой», «аккумуляторный», «акб») | ручной/LLM-маппинг на `qualityDescription` | подсказки в промпте LLM-2 и контроль |

### 3.11 Тест-кейсы для проверки «на глаз» (из выгрузок СТЕ)
Выгрузки СТЕ — это карточки, а не запросы. Делаем из них реалистичные запросы:
1. выбрать 20–30 СТЕ на категорию, **у которых есть подходящее семейство КТРУ** (например: шуруповёрт, УШМ, дрель, электролобзик, молоток, пила; столы, шкафы, стулья; спецодежда, куртки, брюки);
2. LLM переписывает карточку в свободный текст поставщика в 3 вариантах: полный / краткий / с пропуском важных характеристик;
3. сохранить в `test_cases.jsonl`: `{id, category, source_ste_id, text, variant, source_characteristics}`;
4. + 10 ручных кейсов на сценарии демо (§9).
Используем для прогона пайплайна и визуальной проверки; метрики не считаем.

## 4. Онлайн-пайплайн

Вход: `text` (уже исправленный модулем опечаток), опционально `session_id`.
Выход: `Result` (§6.3). Состояние сессии — §6.2.

### 4.0 Предпросмотр (код, ~50 мс)
Поиск по индексу (§3.9) → топ-5 семейств со скором. Отдаётся в UI сразу («похоже на…»), пока работает LLM-1. На итоговое решение **не влияет**.

### 4.1 LLM-1: выбор семейства
**Вход промпта:** инструкция + **полный список 263 карточек** (короткая версия §3.8) + отдельный список общих позиций + текст пользователя.
**Режим масштабирования (конфиг `FAMILY_SELECT_MODE`):** `full_list` (по умолчанию) или `top_k` — подаётся топ-30 из поиска §4.0 (для будущего полного каталога).
**Выход (JSON-схема):**
```json
{
  "candidates": [ {"family_id": "<enum всех id>", "score": 0.0-1.0, "reason": "одно предложение"} ],  // 1–3 шт.
  "not_found": false,
  "not_found_reason": null
}
```
Правила промпта: выбирать только из списка; конкретное семейство предпочтительнее общей позиции; общую позицию — только если конкретных нет; `score` — уверенность; `reason` — коротко, со ссылкой на слова из текста.
**Решение:**
- `top1.score ≥ 0.75` и `top1 − top2 ≥ 0.2` → одно семейство;
- иначе берём все кандидаты со `score ≥ 0.4` (до 3) → дальше §4.3 для каждого, различение в §4.5–4.6;
- нет кандидатов `≥ 0.4` или `not_found = true` → §4.2.
Пороги — в конфиг, подбираются на тест-кейсах глазами.

### 4.2 Семейство не найдено
Ответ пользователю: «Не удалось определить тип товара по КТРУ. Уточните, что это за товар, и укажите основные характеристики» + топ-3 из предпросмотра как подсказки «возможно, вы имели в виду…». Если LLM-1 выбрала общую позицию (generic) — показать её как предварительный код с пометкой «конкретной позиции нет», характеристики — только как дополнительные.

### 4.3 LLM-2: разложить текст по схеме семейства
**Вход:** текст + маппинг `id → название, тип, единица (если есть), обязательность` + JSON-схема семейства (§3.6). Ограниченное декодирование (`format`/`response_format = json_schema`).
Если кандидатов-семейств 2–3 — LLM-2 вызывается **параллельно для каждого**.
**Правила промпта:**
- для **каждой** характеристики схемы вернуть `status`:
  - `указано` — значение прямо следует из текста (в т.ч. через очевидный синоним: «болгарка» → Вид «Углошлифовальная машина», «аккумуляторный» → Тип питания «От аккумулятора»);
  - `не указано` — в тексте нет;
  - `противоречие` — текст противоречит любому допустимому значению или сам себе;
- качественные — только значение из `enum`; числовые — число и единица **как написано в тексте**;
- `quote` — **точная подстрока текста**, из которой взято значение;
- всё остальное существенное из текста → `extra`; бренд/модель → отдельные поля; ничего не выдумывать.

### 4.4 Проверка и нормализация (код)
Для каждой характеристики из ответа LLM-2:
1. **Цитата**: проверить, что `quote` встречается в тексте (нормализация пробелов/регистра/ё, допускается нечёткое совпадение ≥ 0.9). Нет — понизить до `weak`.
2. **Числа**: распознать единицу по словарю (§3.10); если единица не указана — взять единицу характеристики КТРУ (из ОКЕИ значения или из названия). Проверить **размерность** (длина ≠ масса) — не совпала → сигнал `UNIT_MISMATCH`, значение `weak`.
3. **Перевод** в единицу ОКЕИ значения КТРУ: `v_base = v × factor(unit_user) / factor(unit_ktru)`.
4. **Попадание в интервал** с учётом знаков границ (`>`, `≥`, `<`, `≤`, открытые границы); для `concrete` — равенство с допуском 0,5 %.
5. **Уверенность** значения: `confident` = статус `указано` + цитата найдена + (для чисел) единица распознана и размерность совпала; иначе `weak`.
Сохраняем и **исходное значение пользователя** (например, 125 мм), и подобранный интервал/значение КТРУ (для 125 мм у УШМ — «≥125 <130 Миллиметр»: граница 125 включена слева).

### 4.5 Сужение до конечной позиции (код)
Кандидаты = все листья выбранных семейств (1–3).
Для каждого листа и каждой характеристики с `confident`-значением:
| kind | Совместимо, если |
|---|---|
| 1 | значение пользователя = фиксированное значение листа |
| 2 | значение пользователя ∈ списка `allowed` листа (для чисел — попадает в один из интервалов) |
| 3 | все значения пользователя ∈ `allowed` |
| характеристики нет у листа | нейтрально, небольшой штраф |

- Лист **исключается**, если есть хотя бы одно несовпадение по `confident`-значению.
- `weak`-значения не исключают, а дают штраф к скору.
- `score(лист) = score(семейства из LLM-1) × Π(штрафы)`.
- **Воронка** для UI: `все конкретные семейства (263) → семейство(а) → N листьев → 1`, плюс уровень ОКПД2 семейства.

### 4.6 Решение и вопрос (код)
| Ситуация | Действие |
|---|---|
| Остался 1 лист | Итоговый код. Переход к §4.7 |
| Осталось > 1 | Вопрос по лучшей характеристике (ниже) |
| Различаются только семейства (у кандидатов разные `family_id`) | Вопрос «Уточните вид товара», варианты — названия семейств |
| 0 листьев | Конфликт: найти значение(я), из-за которых исключены все листья (для каждого `confident`-значения считаем, сколько листьев оно исключает), показать его и **ближайшее допустимое** значение; предложить исправить |
| > 1 листа и ни одна характеристика их не различает | Показать листья списком, пользователь выбирает (полные дубли встречаются редко) |

**Выбор вопроса.** Для каждой характеристики `c`, по которой оставшиеся листья `L` различаются и значение ещё не известно:
- варианты ответа `V(c)` = объединение значений `c` у листьев `L` (для числовых — интервалы);
- `L_v` = листья, совместимые со значением `v`;
- `P(v) ∝ |L_v|` (или сумма скоров листьев);
- ожидаемый остаток `E(c) = Σ_v P(v) · |L_v|`.
Берём `c` с минимальным `E(c)`; при равенстве — сначала `kind=1`, затем обязательные. Варианты ответа = кнопки `V(c)` + «Не знаю» (тогда берём следующую характеристику). Текст вопроса формируется шаблоном: «Уточните {название}: от этого зависит итоговый код (осталось {N} вариантов)».

**После того как код найден — дозаполнение:**
- `kind=1` — значение берётся из листа (источник «по КТРУ»);
- `kind=2/3`, если у листа единственное допустимое значение — заполняется «по КТРУ»;
- `kind=2/3` обязательная и не указана → список «Нужно дозаполнить» (вопросы-кнопки со значениями листа);
- необязательная не указана → «Можно заполнить» (не навязываем).

## 7. Промпты (шаблоны)

### 7.1 LLM-1 — выбор семейства
```
SYSTEM:
Ты эксперт по каталогу КТРУ. По описанию товара от поставщика выбери подходящее семейство КТРУ
строго из списка ниже. Учитывай разговорные названия и синонимы.
Правила:
- Выбирай только id из списка.
- Конкретное семейство предпочтительнее общей позиции; общую — только если конкретных нет.
- Верни 1–3 кандидата с уверенностью 0..1 и коротким обоснованием (ссылайся на слова из текста).
- Если ничего не подходит — not_found = true.
СПИСОК СЕМЕЙСТВ:
{family_cards_short}
ОБЩИЕ ПОЗИЦИИ:
{generic_cards}
USER:
Описание товара: «{text}»
```
Список семейств ставить **в начало** промпта (одинаковый префикс → кэш промпта на бэкенде, где поддерживается).

### 7.2 LLM-2 — разложить по схеме
```
SYSTEM:
Ты заполняешь характеристики товара по справочнику КТРУ.
Семейство: {family_name}.
Характеристики (id — название — тип — единица — обязательность):
{c01 — Вид — текст — — обязательная}
{c02 — Мощность — число — Ватт — необязательная}
...
Правила:
- Для КАЖДОЙ характеристики верни status: «указано» | «не указано» | «противоречие».
- Текстовые значения — только из допустимого списка (очевидные синонимы допускаются: «болгарка» → «Углошлифовальная машина»).
- Числа — как в тексте, с единицей как в тексте.
- quote — точная подстрока из текста, откуда взято значение.
- Всё остальное существенное из текста — в extra (name, value, unit, quote).
- Бренд и модель — отдельные поля. Ничего не выдумывай.

```

## 8. Интерфейсы с другими модулями

### 8.1 Вход от модуля опечаток
Модуль получает **уже исправленный текст**. Если модуль опечаток отдаёт и список исправлений с позициями — пробрасываем в `Result` без изменений (для подсветки в UI). Контракт уточняется отдельно.

### 8.2 Сигналы для модуля ошибок
Ошибки мы не обрабатываем, но **отдаём факты**, которые естественно возникают в пайплайне:
```json
{"type": "VALUE_NOT_ALLOWED | OUT_OF_RANGE | UNIT_MISMATCH | CONTRADICTION | DUPLICATE_VALUE | QUOTE_NOT_FOUND",
 "char": "Диаметр диска", "user_value": "6", "user_unit": "мм", "quote": "6мм",
 "allowed": ["≥115 <125 Миллиметр", "..."], "nearest_allowed": "…", "family_id": "…", "leaf_code": "…"}
```
- `VALUE_NOT_ALLOWED` — значение вне списка допустимых у всех оставшихся листьев;
- `OUT_OF_RANGE` — число не попало ни в один интервал;
- `UNIT_MISMATCH` — размерность единицы не совпала;
- `CONTRADICTION` — статус «противоречие» от LLM-2;
- `DUPLICATE_VALUE` — одна характеристика с разными значениями в тексте;
- `QUOTE_NOT_FOUND` — цитата модели не найдена в тексте (служебный).

## 9. Порядок реализации и проверка

### P0 — ядро (обязательно)
1. Роли позиций, семейства, сигнатуры листьев, различающие характеристики (§3.2–3.5).
2. Таблица единиц + перевод + попадание в интервал с учётом знаков границ (§3.3, §4.4) — покрыть юнит-тестами.
3. JSON-схемы семейств (§3.6), короткие карточки (§3.8, пока без LLM-метаданных).
4. LLM-клиент (OpenAI-совместимый, structured output, кэш) (§5).
5. LLM-1 полный список (§4.1), LLM-2 по схеме (§4.3).
6. Сужение, вопрос, дозаполнение, конфликт (§4.5–4.6).
7. Карточка, состояние, функции `analyze/answer/...` (§4.7, §6).

### P1 — качество
8. LLM-метаданные семейств + ручной просмотр (§3.7) → полные карточки.
9. Индекс и предпросмотр (§3.9, §4.0).
10. Словари из выгрузок СТЕ: единицы, бренды, названия характеристик, значения (§3.10); унификация `extra` (§4.7).
11. Тест-кейсы из выгрузок СТЕ (§3.11).

### P2 — позже
12. Режим `top_k` для полного КТРУ; проблема разрыва языка пользователя и КТРУ на поиске (синонимы из реальных названий СТЕ).
13. Дообучение эмбеддера.
14. Поведение для товаров без позиции в КТРУ (перфоратор, обычные сверла, отвёртки, уровни, наборы — в текущем scope их нет).

## 10. Ограничения и открытые вопросы
- **Покрытие КТРУ неполное**: для многих популярных инструментов (обычные сверла, наборы, перфораторы, отвёртки, диски, уровни) конкретной позиции в scope нет. Сейчас — §4.2 (просим уточнить / общая позиция). Подход для полного КТРУ — P2.
- **Границы категорий**: scope — конфиг (§1.2); при расширении увеличится список семейств → переключить LLM-1 на `top_k` (§4.1).
- **Пороги** (LLM-1, нечёткое сравнение цитат, допуск concrete) — в конфиг, подбираются на тест-кейсах.
- **Structured output** выбранной модели на роутере — проверить до интеграции (§5).
